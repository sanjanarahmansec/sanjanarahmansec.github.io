CASE STUDY 01 · offensive

Case study: A pentest that chained two bugs into read-write access to every customer backup

Client
e-commerce, under NDA
Scope
Storefront, order API v2, admin panel, AWS account
Type
Grey-box web and API test, OWASP ASVS L2
Result
13 findings, all critical and high fixed and retested

The chain

  • IDOR on GET /api/v2/orders/{id}: the API checked the session but never the owner, so any shopper could walk sequential order IDs.
  • One leaked order exposed an internal image_source field, which pointed me to the product image importer.
  • The importer fetched any URL server-side. Aimed at 169.254.169.254, it returned the instance role's temporary IAM keys inside the error message.
  • The role had s3:* on the backup bucket: nightly database dumps, readable and overwritable.

What changed because of it

The team moved to IMDSv2, cut the instance role to a single prefix, and added object-level authorization tests to CI so an IDOR now fails the build instead of reaching production. I wrote the remediation guide with their developers and retested every fix.

How it works

  • Every rule ships with an Atomic Red Team test. A GitHub Action replays the attack in the lab and fails the pipeline if no alert arrives within 5 minutes.
  • Coverage is measured against what was actually tested, not against the whole ATT&CK matrix, so the number can't be inflated.
  • Each rule is tuned against a week of normal lab noise before it ships.

What it showed

Execution and credential access are well covered, because those attacks are noisy on the endpoint. Exfiltration and impact are the blind spots, and that is also where case study 01 ended: the bucket read raised no alert. The next milestone adds CloudTrail rules for exactly that hop.
